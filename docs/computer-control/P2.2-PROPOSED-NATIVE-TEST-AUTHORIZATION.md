## Proposed target and ownership

One **new** Lumina-owned disposable Windows practice window, identified as `P2.2 practice window` plus a fresh run nonce. Create it only after an explicit implementation/test assignment and approval of this record. The isolated test Runtime creates and owns the fixture; the approving owner/client owns the test session. Existing scratchpads, user applications and similarly titled windows are excluded.

Before arming, bind the run nonce, approving client/session, Runtime instance, HWND, PID and process creation identity, window class/generation, desktop/session, child control identities, physical bounds, monitor/DPI/geometry revision and observation source/session to the run. Resolve actual values at runtime; no PID/HWND/title wildcard substitutes for identity. Revalidate before each bounded batch and after every awaited boundary. No handle adoption across restart.

The fixture must have only local inert controls: an editable synthetic text area, a practice button that increments an in-memory counter, a selectable word area and a scrollable synthetic row area. No open/save, shell, link, browser, account, network, message, payment or filesystem functionality. No real contacts, credentials, personal files, production data or external accounts.

## Proposed lifetime and budgets — not yet approved

- One run, one newly created window; proposed maximum **15 minutes** from creation, with at most **100 action admissions** including focus and cleanup. Reserve cleanup budget; exhaustion forbids further task actions.
- Proposed start deadline: **24 hours after explicit approval**, with an absolute timestamp/timezone recorded before arming. End at the earlier approved absolute expiry or the 15-minute run deadline. No automatic extension or reuse after revocation.
- Proposed individual action wait: no more than existing controller 5 seconds; cleanup wait no more than 0.5 seconds per bounded attempt. These limit waiting, not OS-call lifetime. Retain work that outlives them.
- Creation, initial local synthetic data, target-only capture, bounded readback, safe cleanup and normal closure must each be included in approved scope. Use fresh isolated test state, never production memory/configuration or its unresolved marker.
- Normal closure is through the owned lifecycle, not Alt+F4 or arbitrary PID termination. First stop admissions; establish worker settlement/release evidence, then close. If unsafe or unconfirmed, stop automation, preserve uncertainty and request owner intervention. Missing HWND alone cannot establish settlement.
- The target remains visible, identifiable and isolated from sensitive content. Isolation here is a disposable local fixture, not a VM/security boundary. An unexpected modal window, occlusion, screen lock or desktop change ends input eligibility.

## Revocation and emergency behavior

Revoke on Stop, takeover, approving-client disconnect, expiry, target closure, identity mismatch, unexpected focus change, geometry invalidation or loss of reliable observation. Initial authorized focus acquisition is distinct from an unexpected focus loss during a run. Do not automatically reacquire focus after revocation, switch targets, resume or retry an uncertain action. A new explicit authorization is needed for a new run.

Stop/takeover blocks new task admissions independently of model or vision availability. Already-admitted/submitted input cannot be recalled. Partial submission, timeout, exception, cancellation, failed verification and failed cleanup do not prove no effect.

Only safe release of this run's potentially held injected inputs is eligible as cleanup after revocation; it does not rearm task actions. Recheck target/foreground and physical-user conflicts before global release. If release could affect another app or ownership is uncertain, do not inject further input: retain unresolved state and ask for manual assistance. Cleanup cannot be silently broadened to all keys/buttons. Late acknowledgements cannot clear revoked action state or override unresolved evidence.

Do not deliberately steer input to an unrelated app, induce a native partial send or leave a key held to simulate failure. Partial/exception/release-failure injection remains inert initially. Native tests may observe such failures if they occur naturally; any deliberate native fault experiment needs its own reviewed scope.

## Observation, evidence and privacy

Use existing shared perception, with explicit consent for this target only; no second capture loop, full-desktop capture followed by cropping, camera, provider transmission or persistent screenshot recording. If the implementation cannot obtain reliable target-only pixels without unrelated content, block the visual test. Frames remain transient and revocable; no disk screenshots are proposed.

Proposed evidence location: a new exclusive directory `artifacts/computer-control-p2.2-native-<approval-date>-<unique-run-id>/`, created only for a future authorized run. Never reuse or overwrite existing artifacts. Record source hashes, scope digest/expiry, run/action IDs, monotonic times, target identity metadata, admission/submission counts, verification predicates/results, release evidence, outstanding workers and safety-gate failures. No raw private text, user keystrokes, unrelated titles/content, tokens or credentials. Synthetic text can be represented by digest and predefined case ID.

Counts and model assertions are not task success. Readback and post-action observation must establish explicit predicates. OS state readback and fixture events are evidence, not independent security principals or proof that no intermediate side effect occurred. Native tests cannot establish atomic target delivery or zero post-Stop effects; D1 limitations remain visible.
