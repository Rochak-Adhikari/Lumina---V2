# Master engineering plan
Read STATUS.md for current eligibility. This eight-phase roadmap is proposed for owner approval; it does not authorize implementation. ROADMAP.md owns milestone IDs/dependencies/status/effort; phase specs expand tasks. Original plans are preserved.

**Completion definition.** Deliver dynamic observe→propose→validate→admit→execute→observe→verify navigation in ordinary supported Windows user sessions, including unfamiliar interfaces rather than accepted-task recipes. All A–J requirements in ACCEPTANCE_TEST_MATRIX.md are mandatory within the declared envelope: screen understanding; general input; dynamic reasoning; closed loop; multi-step tasks; recovery; Stop/authority; honest status/privacy; real Windows acceptance; resource feasibility.

Required evidence includes native pointer/click/double-click/text/chord/scroll/drag, negative/mixed-DPI/display/focus cases, actual model inference, three ordinary applications including UIA-poor and cross-app workflows, independent final predicates, zero unauthorized admissions/stale dispatch/false success/consequential duplicates in the fixed corpus, and owner-approved resource limits met on the actual laptop. Carry forward the source plan's proposed quality thresholds: at least 90% low-risk navigation and 80% multi-step success, with fixed denominators defined in the matrix. These are release targets for approval, not current results or universal reliability claims.

Elevated/protected/secure-desktop interfaces and unauthorized consequential operations must be explicitly denied. The future WhatsApp/Rohit/call scenario requires correct contact identity, exact immediate approval and observed call-state evidence through an admitted consequential adapter; it is not passed by a mock call or permitted as a real experiment. Controlled receiver tests establish permission behavior only. Model output, native return count and scratchpad success cannot independently satisfy completion.

**Non-goals.** No mobile/cloud/memory/personality/graph work, duplicate task/authority/capture/database system, whole external agent, foundation-model training, shell fallback, direct file-mutation shortcut, permanent admin/UIAccess bypass, production consequential experiment or screenshot archive. Specialist file/browser/dev adapters are optional later consumers, not prerequisites for the minimum general desktop loop.

**Fixed sequence.** P0 source truth (this static audit); P1 action/observation/geometry contracts; P2 native ordinary input; P3 replaceable model qualification; P4 dynamic loop; P5 verification/recovery/privacy hardening; P6 full product/ordinary-app/resource integration; P7 blind acceptance/release. Observation binding and baseline Stop policy precede native expansion. P3.1 can develop after P1.1 independently of P1.2/P2, but live P3.2 waits for native primitives. P5 completes the fault envelope; it does not postpone basic safety until after input. Original open-ended Phase 8 broadening is removed from this release. UI work cannot replace a missing engine.

**Effort and schedule.** One owner/developer plus one coding model, one editor at a time. Active day = about six focused engineering hours; machine execution/inference waiting is measured separately. P0 audit/planning allowance 1–2 days, now delivered statically. Remaining register totals 30–54 active days including ordinary debugging, integration and native testing. Reserve 25–40% (roughly 8–22 days) for model/Windows/acceptance failures: about 38–76 active days or 228–456 focused hours remaining. Approximately 8–16 full-time workweeks, or 15–31 weeks at 15 focused hours/week, excluding waits for authorization, hardware or providers. Model/native-app phases have low confidence. A blocked $0 model may extend calendar time indefinitely; no hardware upgrade, paid API or fixed delivery date is assumed.

**Plan maintenance.** Approving major phases does not approve every native target/provider transmission. Execute one explicitly assigned milestone unless an owner-approved batch names several. Fix routine evidenced defects inside the current row. Necessary extra work receives a stable child ID under the existing phase with dependencies/gate/risk/effort/matrix updates; do not renumber or add phases silently. Major architecture/completion/security/model/license changes require owner approval with alternatives and critical-path impact; unaffected work may continue. A failed release gate stays incomplete; no ninth phase or diluted corpus.

D1: accept practical ordinary-input semantics before P2 native expansion. D2: choose a viable zero-cost model/privacy trial before P3.2. D3: trusted approval and per-operation evidence before production R3 enablement, which remains disabled in this release by default. These gates do not prevent pure contract implementation after plan approval. First implementation assignment is P1.1, fake-only; do not repeat a full audit.
